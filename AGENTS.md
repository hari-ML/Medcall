# AGENTS.md

MedRecall — turns a prescription photo/PDF into a verified, trilingual (en/ta/hi) medicine schedule. Core product rule: **never guess** (see "Safety rule"). It is enforced by tests *and* by regex audits that parse the source — refactors can break the audit even when behavior is correct.

## Layout

- `backend/` — FastAPI + SQLAlchemy/SQLite. Entrypoint `app/main.py` (assembly only). Run every backend command from `backend/`.
  Pipeline: `ocr.py → extract.py → parser.py → uncertainty.py (the gate) → translate.py → schedule.py / pdf.py`.
  Structure (Phase 1/2/3/4/5/6): `app/main.py` wires routers + the dispatcher lifespan; `app/core/` holds `config.py` (settings, env, upload dir), `logging.py`, `middleware.py` (request-ID), `security.py` (JWT/OTP/signed image URLs + admin tokens/credential verify/lockout), `deps.py` (phone normalisation, `get_current_patient`, `get_current_admin`); `app/routers/` holds `auth.py`, `patients.py`, `prescriptions.py`, `reminders.py`, `agent.py`, `admin.py` (read-only ops console), `system.py`, `serializers.py`; `app/agent/` is the read-only care agent (`context.py` verified data via `build_schedule`, `intents.py`, `responder.py`, `llm.py`, `service.py`); `app/reminders.py` is the reminder engine and `app/channels/` the delivery adapters (fake in dev; real WhatsApp/Twilio in Phase 4). Migrations in `alembic/` (baseline `4fe1831b87e1`, Phase 2 `c8b4f272dc02`, Phase 3 `c63b9c2fe09c`, Phase 4 `a489a7b88ae5`, MedRecall 2.0 `b7d21e4a9c30` — adds `patients.preferred_channel`, `reminder_occurrences.patient_action(_at)`; `init_db()` backfills the three columns for `create_all` DBs).
- `frontend/` — React 18 + Vite SPA, styled with the **Cozy design system** (dark monochromatic bento: canvas `#121212`, cards `#1E1E1E`, Inter, tokens in `tailwind.config.js` + `index.css`). 9 routed pages in `src/pages/` (incl. `NotFound`), a floating `components/BottomNav.jsx`, every API call in `src/api.js`, every UI string in `src/i18n.jsx`, session/route-guard (register + OTP) in `src/auth.jsx`. `capacitor.config.json` (+ `@capacitor/*` deps in `package.json`) builds the Android app (appId `com.medcall.ai`, appName `MedCall`, webDir `dist`); the UI stays branded **MedRecall**.
- `scripts/` — three Node verification scripts, run from the **repo root** (Node 18+; they use global `fetch`).
- `sample_data/` — text fixtures + `rx.png` (the PNG is required by `scripts/api_contract.mjs`).
- Docs are accurate against the code: `README.md` (setup, API table, tests), `backend/README.md` (module map, env vars, error codes), `SAFETY_AUDIT.md`, `DEMO_SCRIPT.md`.

There is **no linter, formatter, typechecker, CI, or pre-commit config** in this repo — the verification steps below are the whole story.

## Auth (Phase 2)

Every `/api/*` route except `/api/health` and the two `/api/auth` login routes requires a `Bearer` access token. `scripts/` audits and `tests/conftest.py` log in first (dev mode echoes the OTP code).

- **Auth is registration-first** (MedRecall 2.0): `POST /api/auth/register` (201 new / 200 reclaims an unverified row / 409 if `phone_verified`) sends the first code, then `POST /api/auth/otp/verify`. `POST /api/auth/otp/request` returns **404 `not_registered`** for an unknown number (sign-in never creates an account — the frontend offers a create-account switch). Dev mode returns `dev_code`; production returns **503 `no_channel`** when no provider delivers the code. No passwords — a deliberate, documented deviation. **Auth endpoints only** return structured `{"detail":{"code","message",...}}` errors (`invalid_otp`+`attempts_left`, `otp_expired`, `rate_limited`+`retry_after`, `too_many_attempts`, `already_registered`, `no_channel`); every other route keeps a plain string `detail` (the API contract asserts that). The frontend (`src/api.js`) surfaces `errorCode`/`errorDetail` and maps each code to a localized state (404→switch to register, 409→switch to sign-in, 401→shake + attempts + refocus, 429→cooldown).
- **Registration fields**: full name, 10-digit +91 mobile, `preferred_lang` (`en|ta|hi|te` — the backend accepts Telugu and falls back to English for phrases/UI; the frontend UI stays `en|ta|hi`), `preferred_channel` (`whatsapp|sms` — decides where the OTP + reminders go), optional `caregiver_phone`. Codes are dispatched over the preferred channel, then the other (OTP over WhatsApp/SMS only; voice cannot carry a readable code).
- **Tokens**: access JWT 15 min (PyJWT, HS256) + rotating refresh JWT 30 d in an httpOnly `SameSite=Strict` cookie `medrecall_refresh` (path `/api/auth`, `Secure` in production). `POST /api/auth/refresh` rotates; replaying a consumed jti revokes the patient's whole token family (theft response). `POST /api/auth/logout` ends the session.
- **Isolation**: every prescription endpoint is scoped to the caller. Someone else's id — or a legacy row with `patient_id NULL` (orphan) — is a plain **404, never 403**, so record existence doesn't leak. `GET /api/prescriptions` lists only the caller's rows, newest first.
- **Images**: the public `StaticFiles` mount for `/uploads` is gone. `image_url` in responses is a signed, 15-minute expiring URL (`?exp=&sig=`, HMAC over `prescription_id:filename:exp`, `core/security.py::sign_image_url`), served by `GET /uploads/{filename}` without a Bearer token so `<img src>` still works. Unsigned/forged/expired → 403; unknown file → 404.
- **New tables**: `patients`, `otp_codes` (HMAC-hashed, 10-min expiry, 5 attempts/code, 5 requests/phone/15 min → 429), `refresh_tokens` (jti registry), `consent_records` (whatsapp/sms/voice — the hard pre-send gate for Phase 3+; default deny).
- **Migration ops for an existing DB** (created by `create_all` before Phase 2): `alembic stamp 4fe1831b87e1` then `alembic upgrade head`. If a Phase-2 server already started against it, its `create_all` pre-created the 4 new tables — stop the server, drop `patients`, `otp_codes`, `refresh_tokens`, `consent_records` (FKs off), then `alembic upgrade head`. Old prescription rows stay NULL orphans (invisible to all accounts).
- **Frontend note (Phase 7)**: the React SPA now has the login UI — `/login` (phone + OTP, public) and every other route is behind `RequireAuth`. The access token lives in localStorage (`medrecall:session`); the rotating refresh cookie stays httpOnly. `src/api.js` injects `Authorization` via a bridge registered by `AuthProvider` and does ONE silent refresh + retry on 401 (never on `/auth/` URLs). The SPA proxies `/api` and `/uploads` to `:8000`.

## Reminders (Phase 3)

`app/reminders.py` materialises the timetable into `reminder_schedules` and dispatches `reminder_occurrences`; `app/channels/` holds the adapters. **Nothing in this layer can create a reminder for an unclear or as-needed item** — eligibility always goes through `is_scheduleable()` and `is_as_needed()`.

- **Enrollment**: `POST /api/prescriptions/{id}/reminders/enroll` creates one schedule per fixed daily slot (`08:00/13:00/18:00/21:00` local) for items in `{clear, confirmed, edited}` that are not SOS/PRN. Unclear/as-needed/no-slot items are returned in `skipped` with a reason. Re-enrolling is idempotent; `DELETE .../enroll` deactivates schedules and cancels pending occurrences (history kept). A confirm/edit after enrollment syncs schedules (`sync_item_schedules`): an edit that re-gates the item to `unclear` deactivates its schedules and cancels pending occurrences; a confirm on an already-enrolled prescription adds the item; a confirm on a never-enrolled prescription creates nothing.
- **Occurrences**: lazily generated up to `HORIZON` (48 h) from local slot times in the patient's IANA timezone, stored as naive UTC (the app-wide convention). Generation is idempotent (`uq_reminder_occurrence_slot`) and capped by `duration_days` (`end_date`).
- **Dispatch**: the dispatcher re-checks before **every** send — (a) schedule active, (b) item still scheduleable and not SOS/PRN, (c) inside the 2 h grace window (older → `missed`, never sent late), (d) explicit per-channel consent. No consent → `blocked` (terminal); unconfigured channel → `failed` (never “sent”). Occurrence statuses: `pending | sent | failed | blocked | missed | cancelled`.
- **Retries (Phase 4)**: transient provider failures (429/5xx/timeouts) increment `attempts` and set `next_attempt_at = now + min(base·2^(attempts-1), cap)`; the dispatcher only retries once that time passes, and stops at `MEDRECALL_REMINDER_MAX_ATTEMPTS` (→ `failed`). Permanent 4xx errors fail immediately. The grace window still bounds the chain — a retry that would be too late becomes `missed`, never sent late. `attempts` and `next_attempt_at` are exposed on occurrence responses.
- **Channels**: preference order `whatsapp → sms → voice`. Development defaults to `FakeChannel`, which records the exact body/channel/`fake-*` id on the occurrence row. Real adapters (`whatsapp.py`, `sms.py`, `voice.py`) are credential-gated; until configured, production marks sends `failed`, never pretends delivery. Consent lives in `consent_records` (default deny) via `POST /api/patients/me/consent`.
- **Endpoints**: `POST/DELETE /api/prescriptions/{id}/reminders/enroll`, `GET /api/reminders/upcoming?days=`, `POST /api/reminders/run` (manual tick), `GET /api/reminders/history` — all patient-scoped (someone else's id → 404). A patient language change updates active schedules' `lang`; the message body is rebuilt at dispatch time via `translate.py` (which raises `UnclearItemError` as defense in depth).
- **Lifecycle**: the FastAPI lifespan starts the polling loop (`dispatcher_loop`); `python -m app.reminders --tick` runs one generate+dispatch pass for cron deployments. `tests/conftest.py` sets `MEDRECALL_REMINDER_DISPATCHER=off` so tests drive the engine with fixed clocks. Messages are prefixed `MedRecall:` and contain only stored verified fields — the engine never invents a dose or a time.

## Delivery providers (Phase 4 + MedRecall 2.0)

Adapters are **dumb pipes**: they deliver the dispatcher's exact text and never import the parser/gate/translator/scheduler. All medical content still comes from the verified timetable. Provider selection is `MEDRECALL_CHANNEL_PROVIDER` (also honours plain `CHANNEL_PROVIDER`) = `live | fake | auto` (default `auto`): `auto` uses the fake adapter in development and the real adapters in production; production can never resolve to `fake`.

- **MedRecall 2.0 extras**: real reminders carry **interactive WhatsApp buttons** (`TAKEN_{id}` / `SNOOZE_{id}` / `HELP_{id}`) and an SMS **reply-hint** line; `POST /api/reminders/test` sends one real (no-medical-content) test message over an explicitly consented channel (403 `consent_required` otherwise — default deny stays default deny; 502 when unconfigured). Webhooks in `routers/agent.py`: `GET/POST /api/webhooks/whatsapp` (hub.challenge verify; button replies) and `POST /api/webhooks/sms` (TAKEN/SNOOZE/SKIP/HELP keywords or free text → TwiML ack). Both record the reply on the occurrence (`patient_action` / `patient_action_at`) — the occurrence status vocabulary is unchanged; a snooze creates a new pending occurrence at `scheduled_at + MEDRECALL_WEBHOOK_SNOOZE_MINUTES` (default 30) through the engine (every gate re-checked).
- **OCR (MedRecall 2.0)**: `ocr.py` first tries **Gemini Vision** (`google-genai`, `gemini-2.5-flash`, `GEMINI_API_KEY`) after **OpenCV shadow removal** (dilation + median-blur background subtraction + normalisation + adaptive-Gaussian threshold), returning strict JSON (`raw_text`, `medicines[]` with `name/dosage/frequency/times/meal_instruction/duration_days/confidence/uncertainty_reason`). The model's output is **synthesized into parseable lines in `parser.py`** and fed through the same extract→parse→gate pipeline — model `confidence` can never set a status, and a model `uncertainty_reason` caps confidence at 0.69 (below the 70 gate) so the item is flagged unclear. No API key → automatic Tesseract fallback.

- **WhatsApp Cloud API** (`channels/whatsapp.py`): `MEDRECALL_WHATSAPP_TOKEN` + `MEDRECALL_WHATSAPP_PHONE_NUMBER_ID`; sends free-form text by default, or an approved template with one body parameter when `MEDRECALL_WHATSAPP_TEMPLATE_NAME` is set (required outside WhatsApp's 24 h service window). Phone is sent as digits only.
- **Twilio SMS** (`channels/sms.py`): account SID/auth token/from; posts `To`/`From`/`Body`, returns the provider `sid`.
- **Twilio voice** (`channels/voice.py`): same credentials under `MEDRECALL_VOICE_*`; builds TwiML `<Say>` with XML-escaped text and a configurable language map (`MEDRECALL_VOICE_LANG_MAP`, default `en:en-US,ta:ta-IN,hi:hi-IN`). TTS coverage for a given language depends on the provider.
- **Errors**: `ChannelDeliveryError.transient` classifies 429/5xx/timeouts (retry with backoff) vs other 4xx (fail immediately). A 2xx without a provider message id is treated as a permanent failure so a dose reminder is never duplicated by a blind retry. Provider error text is truncated and never includes credentials.
- **Testing**: `tests/test_channels.py` mocks all HTTP (`httpx.MockTransport`) — no test contacts a provider. `tests/test_reminders.py` covers the backoff lifecycle. Fake channels remain the dev/test default; `use_fake_channels` is impossible in production.

## Safety rule (preserve invariants — tests + audit enforce this)

- Only the gate (`uncertainty.py`) may produce status `clear`/`unclear`. There is **no code path from `unclear` to `clear`**; humans produce `confirmed` (PATCH `confirm`) or `edited` (PATCH `edit`, which is re-parsed **and re-gated** — an incomplete edit stays `unclear`).
- `SCHEDULEABLE_STATUSES = {clear, confirmed, edited}`. `schedule.py`, `pdf.py`, `translate.py` and `reminders.py` all filter through `is_scheduleable()`; `translate.py` raises `UnclearItemError` as defense in depth. Unclear items never reach schedule, PDF, or reminders — `tests/test_schedule_safety.py` proves the first two, `tests/test_reminders.py` the third.
- The audit's **part A greps source text**, so these patterns are load-bearing: `gate(parsed)` in `seed.py`; `item.status = STATUS_CONFIRMED/STATUS_EDITED/STATUS_UNCLEAR` (never `STATUS_CLEAR`) in the API layer (`app/main.py` + `app/routers/*.py`); `EditFields` must contain no `status` field; `is_scheduleable(` ≥3× in `schedule.py`; frontend never assigns `.status` (except `api.js`), never writes literal statuses, never defines `instruction:` outside `i18n.jsx`.
- **Patient-data isolation (Phase 2)**: every prescription route goes through `_get_owned_prescription` — other patients' rows and NULL-`patient_id` orphans are indistinguishable from missing (404, never 403, no existence leak); only the caller's rows appear in `GET /api/prescriptions`; uploads and demo stamp `patient_id`. `tests/test_auth.py` proves it.
- **Reminders (Phase 3)**: enrollment skips unclear/as-needed/no-slot items; the dispatcher re-checks schedule active + `is_scheduleable` + not `is_as_needed` + grace window + explicit channel consent immediately before each send; no consent → `blocked` (terminal), unconfigured provider → `failed` (never “sent”); the body is rebuilt from stored verified fields and `translate.py` raises for unclear items. `tests/test_reminders.py` proves each gate, including edit-to-unclear cancelling pending occurrences.
- **Delivery (Phase 4)**: channel adapters are dumb pipes — they never import the parser/gate/translator/scheduler and send the dispatcher's text unchanged (audit A11). Transient provider errors retry with exponential backoff (`next_attempt_at`), permanent 4xx fail immediately, and a 2xx without a provider message id is never retried (no duplicate dose). Fake channels are impossible in production (`use_fake_channels`).
- **Care agent (Phase 5)**: `app/agent/` is read-only (no `db.add/commit/delete`), imports no parser/OCR/seed/PDF code, and answers from the same `build_schedule`/`is_scheduleable` used by the timetable/PDF. Unclear items are only named — never given a dose, frequency or time; SOS/PRN items are described as having no fixed time. It refuses dose changes, interactions and diagnosis, and escalates side effects/emergencies. The optional LLM receives verified context only (no `source_text`, phone, image or unclear-item dose) and its answer is rejected unless every number/unit/time/number-word is present in the verified context (`llm.is_safe_answer`); rejection falls back to the deterministic answer. `tests/test_agent.py` + audit A12/B13 prove it.
- **Admin dashboard (Phase 6)**: `app/routers/admin.py` is strictly read-only (no `db.add/commit/delete` — audit A13 greps it) and only *views* data through the same serializers; it never confirms, edits, enrolls or sends. Admin auth is a separate credential (env, HMAC + `compare_digest`, 5-tries/15-min lockout) and a separate token type (`type=admin`, `sub=admin`, 8 h): patient tokens are rejected on `/api/admin/*` and admin tokens on patient routes (401 both ways), and unconfigured credentials fail closed (login 503, routes 401). The admin occurrence feed only ever *shows* stored rows — it cannot create or dispatch one. `tests/test_admin.py` + audit A13/B14 prove it.
- **Web UI (Phase 7)**: the SPA is a thin, read-mostly client of the same APIs — it never assigns item statuses or invents instructions (audit A9 greps `src/`, only `api.js` may write `.status` for its own request bookkeeping, and no file outside `i18n.jsx` defines `instruction:`). `/login` is the only public route; everything else renders behind `RequireAuth`, and `frontend_verify.mjs` server-renders all 8 routes in en/ta/hi with an explicit `initialSession`. The Reminders screen only *displays* backend rows and flips consent (default deny stays default deny); the Timetable's enrollment card calls the Phase 3 API whose `skipped` list (unclear/as-needed/no-slot) is shown with reasons, never silently dropped; the Agent screen renders only what `/api/agent/chat` returns (disclaimer + escalation banners always visible). Browser Notification reminders (tab must be open) were kept alongside server reminders, never replacing them.
- Never weaken the gate to make OCR/demo output look better — flag-and-require-human-confirmation is the intended behavior.

## Frontend/i18n gotcha

Every UI string must exist in **all three** tables (`UI.en`, `UI.ta`, `UI.hi` in `src/i18n.jsx`); `frontend_verify.mjs` fails on key-set drift, empty strings, or a `t('key')` with no `UI.en` entry. Adding a translation only to English will fail verification.
